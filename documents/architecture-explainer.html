01 — End-to-end pipeline

เส้นทางข้อมูล: predict → validate → distribute → render

ทั้งระบบเป็นแบบ decoupled — ไม่มี API server. Backend ผลิตไฟล์สัญญา forecast_provinces.json หนึ่งไฟล์ แล้ว Frontend ไปอ่าน. นี่คือทั้งสาย:

download_indices.py

Tmax, soil moisture L1/L3, MJO, Niño3.4

TRAIN

โมเดล pooled

PREDICT

ออก forecast

predict_provinces.py

→ docs/forecast_provinces.json

GATE

validate (hard)

validate_contract.py

schema=1, 77 จังหวัด, lead {2..6}, ranges, risk enum

DISTRIBUTE

publish_bridge

publish_bridge.py --publish

→ frontend public/ (dev) + contract repo → GitHub Pages (prod)

RENDER

HeatMAP UI

deepseekContract.ts
app/(tabs)/*

Hard gate = ถ้า contract ผิด schema/ช่วงค่า/จำนวนจังหวัด → abort ไม่ distribute. ข้อมูลเสียจึงไปไม่ถึงผู้ใช้.

03 — วิธีคิดของ ML

ทำไมโมเดลถึงเชื่อถือได้

นี่ไม่ใช่ deep learning กล่องดำ — เป็น classical ML บนข้อมูลตาราง ที่ออกแบบรอบ ๆ ความซื่อตรงทางสถิติ (rigor). หัวใจอยู่ที่ 4 ความคิด:

① พยากรณ์ "ความน่าจะเป็น" ไม่ใช่ใช่/ไม่ใช่

target รายสัปดาห์ = มีวัน heatwave ≥1 วันในหน้าต่าง 7 วัน ที่ lead 2–6 สัปดาห์. โมเดลคืน p ∈ [0,1].

y_rm_l{L} = 1 if any heatwave-day in week@(issue + L·7d)

โมเดล pooled ตัวเดียวเรียนข้ามทุกจังหวัด (~828k แถว) — จังหวัดที่เหตุการณ์น้อยยังได้สกิลจากการแชร์

② Features = antecedent-only (กัน leakage)

ทุก feature คำนวณจากข้อมูล ≤ วันออกพยากรณ์เท่านั้น:

// local (ราย cell) sm1/sm3 mean7/mean30/trend, tmax_mean7, in_hw_today (trailing streak ≥3), hot_frac7 // shared mjo_*, nino34_lag1m, doy_sin/cos // static lat, lon, region(one-hot×6)

ห้ามใช้ค่าวันเป้าหมาย / base_rate ดิบ → กัน target leak

③ Calibration — เหตุผลสำคัญที่สุด

บทเรียนจริงในโปรเจกต์: lgbm ดิบ AUC ดี (0.69–0.76) แต่ BSS ติดลบทุก lead — เพราะ "ลำดับ" ดีแต่ "ตัวเลขความน่าจะเป็น" ไม่ตรงความจริง. แก้ด้วย Platt scaling บน block แยกเวลา. กดปุ่มดูผล:

p ดิบ (overconfident) p หลัง calibrate เส้นประ = ความถี่จริง
0.2
0.4
0.6

เมื่อโมเดลบอก "0.6" มันควรเกิดจริงราว 60% ของครั้ง — calibration ดันแท่งเขียวให้ตรงความถี่จริง จึงทำให้ BSS (Brier Skill Score) เป็นบวกและเอาชนะ baseline ได้

④ Validation = ต้องชนะ baseline อย่างมีนัยสำคัญ

ถ้าทายไม่ดีกว่า "อากาศปกติตามฤดู" + "เมื่อวานเป็นยังไง" ก็ไร้ประโยชน์. เกณฑ์ผ่าน = ชนะทั้ง climatology และ persistence (paired test, q<0.05).

โมเดลlead 23456
logistic+0.168+0.109+0.118+0.050−0.014
lgbm_cal+0.144+0.156+0.059+0.024+0.103
persistence (baseline)+0.095+0.048+0.047+0.024+0.017

ตัวเลข = BSS เทียบ seasonal climatology (regional p90). ยิ่งบวกยิ่งดี. Feature สำคัญสุด: nino34_lag1m > sm1_mean30 — ตรงสมมติฐาน ENSO + ความจำความชื้นดิน.

⑤ จาก probability → ป้ายความเสี่ยง

risk_level() ไม่ได้ตัดที่ค่า p ตรง ๆ แต่ใช้ อัตราส่วนต่อ base_rateของจังหวัด (p / climatology_base_rate) — "เสี่ยงกว่าปกติกี่เท่า":

Low · ต่ำ
p<0.05 หรือ ratio<0.75
Normal · ปกติ
ratio < 1.5
Elevated · สูง
ratio < 2.5
High · สูงมาก
ratio ≥ 2.5
ตัวอย่างจริงจาก contract: กรุงเทพฯ lead 2 → p=0.386, base_rate=0.114, ratio=3.4 → High / สูงมาก.
04 — Backend ↔ Frontend

เชื่อมด้วย "สัญญาข้อมูล" ไฟล์เดียว

รอยต่อทั้งหมดคือ forecast_provinces.json (schema_version 1). Backend ไม่รู้จัก React; Frontend ไม่รู้จัก Python. ทั้งคู่ตกลงกันแค่ "รูปร่าง JSON".

// deepseekContract.ts
export function assertContract(c) {
  if (c.schema_version !== 1)
    throw new Error(`schema_version ไม่รองรับ`);  // ปฏิเสธทันทีถ้า schema เปลี่ยน
  return c;
}
export function mapPoints(c) {           // JSON ดิบ → จุดบนแผนที่
  return c.provinces.map(p => {
    const f = p.forecasts.find(x => x.lead_weeks === 2);
    return { province_id: p.id, lat: p.lat, lon: p.lon,
      risk_level: toRisk(f.risk_level_en),    // High → 'extreme'
      target_date: addDaysISO(p.issue_date, f.lead_weeks*7) };
  });
}
